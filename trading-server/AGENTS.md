# Trading Server — Agent Instructions

루트 `AGENTS.md`를 함께 따른다. 기본 수정 소유 범위는 `trading-server/**`; Content·Frontend·루트 인프라는 승인 없이 수정하지 않는다.

## 책임과 경계

- Binance 데이터로 서버 기준 가격을 관리하고, 모의 선물 주문·체결·포지션·잔고·청산·시세 이벤트·원장을 소유한다.
- PostgreSQL `trading` Schema만 소유한다. Content 회원 데이터를 직접 조회·변경하지 않으며 검증된 회원 JWT의 `memberId` 및 명시적 서버 간 계약으로 연결한다.
- Redis 시세 Snapshot·Stream·캐시 유실과 재처리를 고려한다. 금융 데이터의 원본은 PostgreSQL이다.

## 반드시 지킬 금융 불변조건

- 주문·체결·강제청산·손익·수수료·증거금의 최종 근거는 **서버 가격과 서버 거래 정책**이다. 클라이언트 계산이나 외부 입력을 체결 결과로 신뢰하지 않는다.
- Account Lock, DB Transaction, 주문 멱등성 키, 원장 유일성 제약, 취소·체결·청산 경합 방어를 검증 없이 제거하지 않는다.
- 작업 실패나 이벤트 중복 재생으로 이중 체결·이중 출금·음수 잔고 왜곡·중복 수량 청산이 발생하지 않아야 한다. 오류 시 함께 변경된 금융 상태가 원자적으로 롤백되어야 한다.
- 오래된 시세·미복구 Stream·위험 미평가 상태에서 거래를 허용하도록 안전 게이트를 우회하지 않는다. 계정 잠금·Worker 경합·장애 복구 테스트를 유지한다.
- 현재 거래 모델은 USDT 모의투자, Isolated Margin, LONG/SHORT Hedge, 부분 청산, LIMIT 예약과 수수료 반영이다. 관련 계약을 바꿀 때 이미 열린 포지션·미체결 주문·기존 이력의 정합성을 먼저 검증한다.
- 레버리지는 **계정·종목·방향별 독립 설정**(기본10, 1~100배)이다. 한 방향 변경 시 반대 방향·다른 종목·과거 체결 사실을 보존한다. 해당 방향의 포지션 담보와 PENDING OPEN 예약을 공통 지갑 자금·수수료 검증 아래 원자적으로 재배정한다.
- Guest는 7일짜리 opaque Bearer Token, 회원은 Content 서명 RS256 JWT다. Guest/회원 계정 소유권과 기록을 섞지 않는다.
- Guest 재도전과 회원 회차 재시작은 과거 체결·원장을 보존한다. 행정적 포지션 종료를 허위 체결·PnL로 기록하지 않는다. 회원 재시작은 24시간 정책을 따른다.
- 금융 상태 또는 DB 마이그레이션의 임의 재설정·삭제를 금지한다. 이미 적용된 Flyway Migration은 수정하지 않는다.

## 작업과 검증

- 현재 구현과 기존 회귀 테스트를 우선 재사용한다. 근거 없는 전체 재설계를 피하되, 재현된 처리 적체를 해결하는 데 필요한 조회·작업 처리 구조 개선은 승인된 범위 안에서 수행한다.
- 계정·주문·포지션·증거금 정책 변경 시 동시 실행, 재시도, 실패 롤백, 중복 이벤트 및 과거 데이터 호환성을 검사한다.
- 신규 운영·Scale-Out 구조를 실제 요구사항 없이 미리 도입하지 않는다. 현재 단일 노드 실행의 안전성을 우선 보존한다.
- 빌드/테스트: `./gradlew clean build` (Docker/Testcontainers 요구 가능). API 및 실행 설정은 [`README.md`](README.md)와 실제 Controller/Runtime OpenAPI를 확인한다.
- Git·PR·기존 MD 갱신 제한은 루트 `AGENTS.md`를 따른다.

## 가격·체결·수치 정책

- 금융 계산은 BigDecimal을 사용하며 float/double을 금지한다. 가격·수량·금액·PnL·수수료의 단위, scale, 반올림을 TradingMath 등 기존 계약과 일치시킨다. 원본 계산값과 표시 반올림을 구분한다.
- 신규 거래는 fresh 서버 Mark Price를 기준으로 한다. 호가·Frontend 가격을 실제 체결가로 신뢰하지 않는다. 시장가도 Order/Fill을 남긴다.
- LIMIT OPEN은 LONG 요청가격 < 현재 Mark, SHORT 요청가격 > 현재 Mark일 때만 접수한다(같으면 거부). 체결 조건은 LONG Mark <= limit, SHORT Mark >= limit이며 실제 crossing Mark로 체결한다. 가격의 정확한 일치만 기다리거나 항상 지정가로 체결했다고 기록하지 않는다. LIMIT CLOSE는 대상 포지션의 반대 매매 방향 계약을 따른다.
- 신규 주문의 담보와 예상 수수료를 함께 예약하고 실제 체결 시 재검증한다. 청산 예약 수량과 신규 진입 예약 자금을 혼동하지 않는다. 추가 진입·취소·부분청산·강제청산·레버리지 변경의 경합을 검증한다.
- Isolated 포지션 위험은 반대 방향·다른 종목·미사용 지갑 자금으로 자동 보전하지 않는다. 실제 손익·수수료·격리 손실 조정액을 구분한다. 기존 Cross 이력의 의미를 보존하고 안전 전환 불가 상태를 숨기지 않는다.
- 현재 포지션의 미실현손익/ROE, 기간별 실현 성과, 회차 수익률, 재시작 자본조정은 서로 다른 값이다. 확인되지 않은 초기금이나 종목 수익률을 임의 생성하지 않는다.

## 영속 위험 작업과 성능 검증

- 수신한 가격의 PostgreSQL journal과 계정별 작업이 복구의 근거다. Redis Snapshot/Stream은 영구 위험 기록의 유일한 원본이 아니다. 계정별 순서와 DONE 기록·금융 정산의 동일 트랜잭션을 유지한다.
- 정상적으로 수신·기록한 과거 이벤트 재처리와 현재 주문의 freshness를 구분한다. 놓친 crossing을 처리하기 위해 오래된 가격을 일반 주문에 허용하지 않는다.
- 미수신 가격 경로는 추측하지 않는다. 운영 검토 hold와 근거를 보존하고 자동 재시도는 유한해야 한다. 실패 계정이 정상 계정의 처리 비용·진행을 계속 방해하지 않게 한다.
- 정상 계정/보류 계정 및 누적 이력이 섞인 실제 크기의 데이터로 실행계획과 지연을 측정한다. LIMIT가 있다는 이유만으로 조회 비용이 제한된다고 가정하지 않는다.
- 적체 수정은 10만 건 이상 보류 이력과 지속 시세를 포함한 최소30분 시나리오에서 대기량·최고 대기시간이 악화되지 않고 일시 부하 뒤 회복되는지 확인한다. 환경·유입률·계정 수와 p50/p95/p99를 기록한다. 이 기준은 현재 적체 수정 검증이며 모든 단순 수정에 부하 테스트를 반복할 필요는 없다.
- 원장 대사는 금융 값을 자동 보정하거나 가짜 Fill을 만들지 않는다. 불일치 hold 해제는 원인 해결과 근거 있는 검토 절차를 따른다.
- 시세 연결은 사용자 수와 독립적으로 중앙 관리한다. 재연결 backoff/jitter, 구독 복구, 중복 연결·중복/역순 이벤트, 종료와 공급자 제한을 처리한다. 외부 규칙 변경은 구현 시점의 공식 문서로 확인한다.
- 실제 사용자 DB의 migration은 대상·버전·백업·구버전 앱/worker 중지 조건을 확인하고 승인 범위에서 수행한다. V18~20 전환 중 구버전 혼합 실행은 금지한다. 일반 회귀는 격리 PostgreSQL/Redis에서 실행한다.
