# Frontend Agent Rules

## 1. 기본 기술

- Next.js App Router
- TypeScript
- Tailwind CSS
- TradingView Lightweight Charts
- HTTP 통신은 기본적으로 native fetch를 사용한다.
- 서버 상태 관리가 필요할 경우 TanStack Query를 우선한다.
- Redux는 명확한 필요성이 있을 때만 사용하며, 도입 전 사용자에게 필요한 이유를 설명한다.
- 항상 더블클릭의 문제를 고려한다.

## 2. 작업 순서

페이지 또는 기능 단위 작업은 반드시 아래 순서로 진행한다.

1. 마크업
2. 디자인
3. 기능 구현

### 마크업
- 해당 페이지의 기능 구현에 필요한 컴포넌트와 HTML 구조를 만든다.
- 버튼, 입력창, 탭, 테이블 등 이후 기능 연결에 필요한 요소를 빠짐없이 준비한다.
- 이 단계에서는 디자인 완성과 API 연동을 하지 않는다.

### 디자인
- 완성된 마크업을 기준으로 Tailwind CSS를 적용한다.
- 반응형, Typography, Spacing, 상태 표현 등을 완성한다.
- 이 단계에서는 API 연동이나 실제 비즈니스 로직을 구현하지 않는다.

### 기능 구현
- 완성된 마크업과 디자인을 변경할 필요가 없는 형태로 기능을 연결한다.
- REST API, WebSocket, 상태 관리, 사용자 이벤트 등의 실제 동작을 구현한다.

마크업, 디자인, 기능 구현을 한 번에 진행하지 않는다.
한 단계가 완료된 뒤 다음 단계로 넘어간다.

## 3. Mobile First

모든 화면은 Mobile First 방식으로 구현한다.

- 모바일 화면을 기본 레이아웃으로 설계한다.
- Tablet과 Desktop은 모바일 구조를 기반으로 자연스럽게 확장한다.
- PC 화면을 먼저 만든 뒤 모바일로 축소하는 방식은 사용하지 않는다.
- 모바일과 PC에서 정보의 중요도와 배치는 달라질 수 있다.

## 4. 디자인

거래소 및 금융 서비스에 어울리는 단정하고 정보 중심적인 UI를 만든다.

피해야 할 표현:

- 과도한 네온 및 Glow
- 불필요한 Gradient
- 무분별한 Box Shadow
- 의미 없는 Hover Animation
- 과도하게 둥근 UI
- 장식 목적의 효과
- 전형적인 AI 생성 SaaS 스타일

Typography, Spacing, Radius 등은 페이지마다 임의의 값을 계속 만들지 않고 일관된 규칙을 사용한다.

## 5. 컴포넌트

- 반복되는 UI와 기능은 재사용 가능한 컴포넌트로 만든다.
- 재사용 가능성이나 책임 분리의 의미가 없는 작은 요소까지 과도하게 분리하지 않는다.
- `app` 라우터 구조는 도메인과 서브페이지 기준으로 단순하게 유지한다.
- URL 구조와 실제 기능 컴포넌트 구조를 불필요하게 동일하게 만들지 않는다.

## 6. Trading 데이터

- Frontend가 체결 가격, PnL, Margin, Liquidation 등의 최종 값을 임의로 결정하지 않는다.
- 금융 Decimal 문자열을 권위 있는 계산을 위해 JavaScript `number`로 함부로 변환하지 않는다.
- Browser에서 Binance에 직접 연결하지 않고 Trading Server가 제공하는 데이터를 사용한다.
- API 연동 시 실행 중인 Trading Server의 `/v3/api-docs`를 계약 기준으로 확인한다.

## 7. 작업 완료 보고

작업이 끝나면 반드시 이번 작업에서 수행한 범위를 명확하게 알려준다.

예:

- 마크업 작업 완료
- 디자인 작업 완료
- 기능 구현 완료

여러 단계가 섞여 있는 것처럼 표현하지 않는다.

추가로 다음 단계에서 해야 할 작업이 있다면 현재 작업과 구분해서 알려준다.

## 8. 변경 원칙

- 요청한 범위를 벗어난 대규모 리팩터링을 하지 않는다.
- 관련 없는 파일, 스타일, 폴더 구조를 임의로 변경하지 않는다.
- 기존 코드가 있다면 현재 구조와 규칙을 우선 파악한 뒤 최소한의 변경으로 작업한다.

## UI 일관성

- 같은 역할의 UI는 같은 디자인 규칙을 사용한다.
- 대제목, 소제목, 본문, 라벨, 버튼 텍스트 등 공통적인 Typography는 페이지마다 임의로 다르게 만들지 않는다.
- 공통 버튼, 입력창, 탭, 카드 등의 높이, 여백, radius도 일관된 기준을 유지한다.
- 필요 없는 일회성 arbitrary value를 남발하지 않는다.
