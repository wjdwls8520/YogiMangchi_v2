## P0 — 위험 작업 적체로 정상 계정의 주문·청산이 막힘

실제 새 Guest에서 시장가 진입, 같은 키 재전송, 부분청산, 지정가 접수·취소까지 성공했다. 이후 `ACCOUNT_RISK_PENDING` 503이 반복돼 후속 주문과 남은 포지션 청산이 막혔다. 재전송은 동일 키를 유지했으며 명확한 복구 대기 응답에만 최대 12회로 제한했다.

읽기 전용 측정에서 운영 검토 hold가 없는 테스트 계정 26/28의 대기가 약31초 동안 각각 **98→118**, **68→88**로 증가했다. 같은 시간 DONE 증가는 각11건뿐이었다. 따라서 단순히 순간적으로 거래를 보류했다가 회복한 사례가 아니다.

`DurableRiskWorker.java:59`의 다음 작업 조회에 EXPLAIN ANALYZE를 실행한 결과:

- 대기 작업 약123,352건 중 실행 가능한 결과2건 반환.
- 조회 한 번 **2,928ms**, shared buffer hit **2,642,245회**.
- 기존 보류 계정들의 누적 작업까지 검사하는 조회 비용이, 보류되지 않은 신규 계정 처리에도 영향을 준다.
- 50ms 스케줄 설정은 실제 50ms 처리 주기를 보장하지 않는다. 이 조회 지연과 계정별 순서 처리 때문에 수신 속도를 따라가지 못했다.

보강: 실행 가능한 계정의 가장 오래된 작업을 먼저 좁히는 조회/인덱스 또는 계정별 작업 큐 구조를 검토한다. 보류 계정과 정상 계정의 조회 비용을 분리하고, 계정 내 순서·정산 원자성·중복 방지는 유지한다. 10만 건 이상 보류 이력과 지속 시세가 함께 있는 장시간 회귀 테스트에서 대기량이 수렴하고 정상 계정의 주문·청산이 회복되는지 검증해야 한다. 자금 보호 조건을 끄거나 hold를 일괄 해제하는 해결은 적절하지 않다.

## P1 — develop Frontend와 새 Backend의 레버리지 계약 불일치

develop Frontend는 `GET .../leverage`에 side를 보내지 않는다. 새 Backend에서 실제 **400**을 확인했다. 따라서 구 Frontend 단위 테스트237개가 통과해도 새 Backend와 함께 사용할 수 있다는 증거는 아니다.

## P2 — 사용자에게 필요한 상태 설명 보강

- 실제 브라우저에서 거래 정상 표시 이후 주문 시도 시 복구 확인 상태로 바뀌고 입력이 잠기는 현상을 확인했다. 거래 가능 여부, 복구 대기, 운영 검토 필요를 사용자 행동과 연결해 안내해야 한다. 서버 적체 해결이 먼저다.
- localhost 브라우저의 기존 회원 세션은 복구됐으나 필수 정책 미동의 상태에서 상단은 재동의를 요구하고 주문 패널은 계속 **회원 로그인 상태를 확인하는 중**이라고 표시했다. 로그인 완료/동의 필요/인증 확인 실패를 구분하고 주문 패널에 정책 확인 경로를 제공해야 한다. 실제 동의 제출이나 기존 회원 탈퇴는 수행하지 않았다.
- `recovery-contract.ts`에 `LEDGER_MISMATCH` 설명이 없어 원장 불일치를 일반 **가격 위험 기록** 검토 문구로 표시한다. 코드로 확인한 문제이며 실제 원장을 훼손해 재현하지 않았다.
- Guest 초기 로딩에서 `Short undefined×`가 잠시 표시된 뒤 정상 값으로 바뀌었다. 설정을 읽기 전에는 숫자 대신 로딩/미확인 표시가 필요하다.
- 390px 모바일 화면에서 문서 전체 가로 넘침은 없었고 차트/주문/거래내역 탭 이동은 가능했다. 거래 표 안의 가로 스크롤은 존재했다. 모든 기기·접근성 요건을 검증한 것은 아니다.

## 제한과 남겨진 상태

- Google/Kakao 외부 인증부터 신규 가입·로그인·탈퇴까지 실제 사용자 전체 흐름은 완료하지 않았다. Content 자동 테스트의 공급자 HTTP는 모의 서버이며 실제 공급자 전체 흐름 성공으로 보고하지 않는다.
- 실제 시세를 조작해 강제청산하거나 Redis/DB를 중단하지 않았다. 해당 장애·청산 검증은 격리 자동 테스트 결과다. 실시간 지정가 crossing 완료와 브라우저 주문→최종 전체청산 흐름은 이번 적체 때문에 전체 통과로 판정하지 않았다.
- 첫 HTTP 검증 스크립트는 Position 응답 필드명을 `positionId`로 잘못 참조해 중단됐고, 실제 계약인 `id`로 수정해 재실행했다. 이는 제품 오류 집계에 포함하지 않았다.
- 테스트 Guest26의 BTC LONG0.001(포지션40), Guest28의 LONG0.0005(포지션41)가 남아 있다. 후속 청산 검증은 복구 대기로 실패했다. 토큰은 출력·파일 보존하지 않았으며, 기존 사용자 계정·잔액·hold를 수동 수정해 정리하지 않았다. 테스트 계정과 이력은 사용자 데이터와 구분해 후속 정리가 필요하다.
- Frontend3000·Content8080·Trading8081은 실행 상태로 유지했다. root `.env` 값은 출력·전송하지 않았고 Content 실행 환경에만 읽어 주입했다. Frontend에는 로컬 공개 서버 주소만 설정했다.
- 애플리케이션 코드 수정, 기존 MD 수정, PR 병합, 커밋·푸시는 수행하지 않았다. 진단 파일은 Git에서 제외되는 `.gradle/qa-20261024`에 저장했고 이 보고서만 신규 문서로 추가했다.
